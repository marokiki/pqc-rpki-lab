Introduction
RPKI, everyone knows it!1 But how well do we know it? Is the RPKI in
good shape? Welcome to the inaugural quarterly technical report for RPKI
professionals!
This series covers observations related to scalability and reliability of the global
RPKI distributed database, comprehensive analysis of incidents in certification
authority and trust anchor operations, and executive summaries of developments
in standardization forums and the field itself. It is hoped that these reports will
contribute toward an interoperable dependable global RPKI.


Methodology
The primary data source for reports is RPKIViews, an open data project aiming
to discover and store all the world’s RPKI objects in their original form. Data is
gathered through a wide array of geographically diverse vantage points using
Rsync and RRDP synchronization transport protocols in parallel. Collection
and analysis are performed using rpki-client, rrdp-tools, and proprietary tooling.
RPKIViews is regarded as the most complete global RPKI capture available.
This report includes various statistics produced from the fully merged and
deduplicated capture dataset. This approach filters out any noise resulting
from retransmissions of data caused by protocol idiosyncrasies and intermittent
network failures between vantage points and publication points.
The IETF SIDROPS mailing list is also used to track ecosystem developments.

Toward understanding global RPKI convergence
Because operators may need to urgently issue or revoke ROAs as part of incident
response, the RPKI’s usefulness depends on the data’s ability to propagate
globally in a timely fashion. When synchronization timeouts occur, any newly
signed ROAs or revocations that are queued up for distribution on the server
side will only become effective after the client’s next successful run. For some
publication points, many more timeout events were observed in the second and
third quarter of 2026 than for other publication points, as shown in Figure 1.

Causes of synchronization issues
A number of factors influence whether a given {publication point, client} pair
can establish a synchronized state:
  • The overall size of the repositories hosted at the publication point.
  • The total number of objects in a repository.
  • The rate at which new objects replace old objects (churn rate).
  • The size of the objects.
  • Packet loss on the connectivity paths between the publication point and
    the client.
The overall size of a repository is the product of both object count and object
size. Object count mostly depends on whether an issuing CA can pack many
payloads into fewer objects. Conversely, the more objects concurrently exist for
a given CA, the larger that CA’s manifest will be. Signed object size follows
from unavoidable factors such as the size of the cryptographic signature and
dynamic factors such as the choice of directory hierarchy and filename naming
scheme. The size of a given CA’s CRL relates to the default validity period of
the certificates the CA issued: the longer the validity period the higher the
chances the certificate will need to be revoked before expiry and the longer the
certificate’s serial remains on the CRL.


                                       2
A CA issuing ROAs containing just a single prefix and using a lengthy naming
scheme and overly long validity periods will see a compounding detrimental
effect: single prefix ROAs incur the maximum possible overhead, directory and
filename strings (long or short) are unavoidably repeated in various fields in the
end-entity certificate and transport layer meta data (Rsync & RRDP), causing
bloat, and many objects means larger manifests and CRLs.
From this it follows that the smaller the set of data that needs to be distributed
from publication point to clients, the higher the chances of swiftly achieving
successful synchronization.

RRDP Statistics
RRDP statistics should be considered separately from the aforementioned
initial state statistics. For example, an object transmitted through RRDP might
not be a valid object and as such not count toward any particular CA system in
the initial state. It is also technically possible to produce internally inconsistent
RRDP deltas in which a coherent state is smeared across multiple deltas, in such
cases the number of deltas will be higher than the number of validation states.
Each RRDP delta is its own XML document containing binary payloads. The
volume represents the total size of the dataset newly presented to clients for
consideration. Actual network traffic will be much higher than the numbers
below might suggest because the these numbers entirely exclude retries and any
waste caused by partial downloads. As such, these numbers represent a lower
bound for network traffic.
While the total number of RRDP deltas did not increase significantly
month-to-month, the total size grew by almost 50%: from 101.8 GiB in the
second quarter to 146.4 GiB in the third quarter of 2026.

RPKI Newswire
This section contains curated news from the field.

ARIN improved standards compliance
ARIN resolved two long-standing standards compliance issues in August 2026.
Background: Leftovers from an older signer implementation (which ARIN
phased out in August 2020) remained in the ecosystem in the form of a few
thousand incorrectly encoded objects.
Specifically, a number of objects were encoded using BER coding (indefinite
length encoding) while the RPKI standards only permit DER coding. The
other issue was that a number of objects incorrectly omitted parameters in
sha256WithRSAEncryption AlgorithmIdentifier instances.
In recent years the RPKI community has taken to reducing variability in
encoding, this cleanup is an important step forward. ARIN was the last to use
BER coding.

AfriNIC improved standards compliance
AfriNIC completed a multi-year project to reissue all non-conformant
certificates in August 2026. See AfriNIC’s final update here.
Background: RFC 6487 section 4 unambiguously specifies: “The CommonName
attribute MUST be encoded using the ASN.1 type PrintableString”, For many
years, however, large CAs incorrectly issued certificates with UTF8String
encoding owing to a documentation bug in OpenSSL.
While the specific choice in RPKI standards for either PrintableString or
UTF8String hardly matters in its context and would almost appear as a minor
cosmetic detail, it is very important for both signers and validators to be on the
same page. For optimal interoperability (now and in the future), the deployed
software and published standards should be fully aligned in order to achieve
byte-for-byte identical outputs for identical inputs in a diverse set of systems.

RIPE NCC RRDP performance issue in Bangalore
In the period August 6 to August 14, and September 7 to September 11, 2026,
RIPE NCC’s RRDP service in Bangalore, India, appeared to often serve
HTTP 503 errors in response to requests for RRDP deltas. An RRDP
webservice emitting HTTP errors will cause RPKI validators to retry by
downloading a full snapshot, and if that also fails try Rsync service.
Table 2 shows that RIPE NCC’s full snapshot is substantial in size. The likely
tangible impact reflected delays in ROA propagation and revocation from RIPE
NCC members toward Indian ISPs.

TWNIC improves RRDP reliability by increasing retention
On August 14, 2026, a number of RPKIViews collectors observed
synchronisation issues due to missing RRDP delta files on TWNIC’s RRDP
publication point. Collectors received HTTP 404 error responses. Typically
this either means new notification files were published before the associated
snapshot/delta files were also made publicly accessible or older snapshot and
delta files were removed too soon.
After having been made aware of the issue, TWNIC staff promptly increased
the retention time for older RRDP material in order to help clients avoid
running into a time-of-check-time-of-use race condition.

IDNIC brief outage
On August 29, 2026, the IDNIC publication point was malfunctioning. A post
hoc analysis of the CMS signing-time attribute contained in the newly
discovered objects retrieved after the publication point became reachable
suggests there was a seven hour delay for newly signed objects.

AfriNIC brief outage
On September 20, 2026 AfriNIC experienced an outage: a critical CRL was not
resigned and distributed before the older version expired, causing all
subordinate products to become invalid. This CRL covers the scope of the
primary online CA for AfriNIC.

RIPE NCC implements policy to revoke non-functional
CAs
On September 24, 2026, the RIPE NCC shared that they had successfully
implemented the RIPE-847 policy which provides RIPE NCC with mandate to
revoke so-called “non-functional CAs”. A CA is considered non-functional when
no valid and current manifest can somehow be retrieved and validated for an
extended period of time.

Standardization News
Stricter validation
Following from BER encoding no longer appearing in the ecosystem and the
presence of UTF8String instances also being a thing of the past, a number of
RPKI validator implementers have expressed an interest to release versions of
their software packages with stricter object validation and standards
conformance checks.
   • BER coding rejection
   • UTF8String rejection

RPKI Trust Anchor Constraints
The SIDROPS chairs declared consensus to progress a configuration format
specification used to constrain RPKI Trust Anchors toward RFC publication.
This is an important step forward for the initiative to better isolate Regional
Internet Registries from each other and provide improved detection capabilities
for “out-of-scope” certificate issuances.

RPKI testing fixture availability
A new vendor-agnostic “RPKI test fixture”, based on snapshots of the global
RPKI, is now available.
The fixture tarballs contain everything an RP needs to perform full chain
validation: the TALs, TA certs, CA certs, signed objects, and a precomputed
CCR to compare against. The fixture is primarily aimed at assisting in the
development and maintenance of cryptographic libraries. Given the scope of the
fixture, validation of the data set ensures a broad set of library functions and
that code paths are exercised. The hope is that this will help detect code
changes that would accidentally negatively impact RPKI applications
(announcement here).
